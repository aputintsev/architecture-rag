# Сравнение LLM-моделей

| Критерий                           | YandexGPT                                                           | OpenAI                                                               | HuggingFace                                                                |
|------------------------------------|---------------------------------------------------------------------|----------------------------------------------------------------------|----------------------------------------------------------------------------|
| Качество ответов                   | Ограниченное для английской техдокументации, фокус на русском языке | Отличное для технической документации, кода и API-описаний (GPT-4o)  | Гибкий выбор моделей под задачу (Llama, Mistral, CodeLlama для кода)       |
| Скорость работы                    | Медленнее из-за удалённости серверов от Европы                      | Быстрая в европейском регионе, стабильная доступность                | Полный контроль: размещение в AWS EKS рядом с данными, низкая задержка     |
| Стоимость владения и использования | Средняя, есть проблемы с оплатой из ЕС; риски санкций               | Высокая при 18K документов и частых запросах (~$50-200/день)         | Экономична при масштабе: только GPU в AWS, окупается за 3-6 месяцев        |
| Удобство и простота развертывания  | Проблемы с юрисдикцией данных (РФ), не соответствует SOC 2          | Простое API, но данные передаются OpenAI (риск для SOC 2 audit)      | Сложнее начально, но полное соответствие SOC 2, данные остаются в компании |

Таким образом, YandexGPT - не подходит из-за юрисдикции РФ. 
OpenAI обеспечивает отличное качество для технической документации, но имеет очень высокую стоимость при объемах компании (18K документов).  
HuggingFace (Llama 2 13b) - оптимальный выбор: полный контроль над данными, размещение в существующем AWS EKS, экономическая выгода при масштабе, гибкость выбора моделей под задачи (включая специализированные для кода).

# Сравнение моделей эмбеддингов

| Критерий                           | локальные Sentence-Transformers                                                                      | облачные OpenAI Embeddings                                                       |
|------------------------------------|------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------|
| скорость создания индекса          | Средняя: для 18K документов ~2-4 часа на GPU в EKS                                                   | Быстрая через API, но ограничена rate limits; для 18K документов ~30-60 минут    |
| качество поиска                    | Хорошее: модели all-mpnet-base-v2, e5-large для технических текстов; можно тонко настроить под домен | Отличное: text-embedding-3-large/small — лучшие универсальные модели для RAG     |
| стоимость владения и использования | Низкая: только GPU в AWS (~$1-3/день), либо производительная видеокарта                              | Высокая: ~$5-10/день для индексации + переиндексации; данные уходят к OpenAI     |

Для QuantumForge Software с требованиями SOC 2 и большим объемом документации локальные Sentence-Transformers выглядят предпочтительнее.

# Сравнение векторных баз ChromaDB и FAISS

| Критерий                                 | ChromaDB                                                                                                                              | FAISS                                                                                                                      |
|------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------|
| скорость поиска и индексации             | Хорошая “из коробки” для типичных RAG-нагрузок (десятки/сотни тысяч чанков).                                                          | Очень высокая производительность. Часто быстрее и эффективнее по памяти на больших объёмах.                                |
| сложность внедрения и поддержки          | Низкая: готовая векторная БД с API, персистентностью, коллекциями. Можно поднять в уже имеющемся EKS.                                 | Средняя: это библиотека, а не БД. Нужно самостоятельно писать обвязку: API, работа с метаданными, фильтрация.              |
| удобство в работе                        | Высокое: удобные операции добавления/удаления, метаданные, простая интеграция с RAG-фреймворками, фильтры по полям                    | Среднее: сильная сторона — векторный поиск. Но метаданные и фильтры отсутствуют из коробки.                                |
| стоимость владения (учет инфраструктуры) | Обычно ниже для команды: меньше инженерных часов на поддержку (готовый сервис). По ресурсам — умеренно, масштабируется горизонтально. | По стоимости вычислений может быть очень экономичен, но стоимость владения высокая из‑за необходимости разработки обвязки. |

По совокупности критериев ChromaDB выглядит более предпочтительным выбором для внутреннего инструмента для быстрого старта. В случае сильного роста количества документов в будущем можно будет перейти на FAISS.

# Выбор конфигурации сервера

## Вариант 1 - Облачное решение
LLM и эмбеддинги от OpenAI, ChromaDB как векторная БД.
GPU не нужен, достаточно CPU для API сервиса обвязки.
- Сервис: 4-8 vCPU, 16 Gb RAM
- ChromaDB: 8 vCPU, 32 Gb RAM, 150 Gb SSD  

Такое решение позволит максимально быстро запуститься и обеспечит высокое качество генерации, но завязано на внешнего провайдера LLM, что, во-первых, дорого, а, во-вторых, не удовлетворяет требованиям хранения данных у себя.

## Вариант 2 - Гибридное решение
Облачный LLM, локальные эмбеддинги от HuggingFace, ChromaDB как векторная БД.
- Сервис: 4-8 vCPU, 16 Gb RAM
- Embeddings: 1x16 Gb VRAM, 8 vCPU, 32 Gb RAM
- ChromaDB: 8 vCPU, 32 Gb RAM, 150 Gb SSD

Дешевле, чем вариант 1, но остается зависимость от внешнего провайдера LLM. Это создает риски комплаенса из-за того, что контекст вопроса уходит вовне.

## Вариант 3 - Полностью self-hosted решение
OpenSource LLM (например, Llama 2 13b), локальные эмбеддинги от HuggingFace, ChromaDB как векторная БД.
- Сервис: 4-8 vCPU, 16 Gb RAM
- LLM inference: 1x24 Gb VRAM, 8-16 vCPU, 32 Gb RAM
- Embeddings: 1x16 Gb VRAM, 8 vCPU, 32 Gb RAM
- ChromaDB: 8 vCPU, 32 Gb RAM, 150 Gb SSD

Максимальный контроль данных и предсказуемая стоимость на масштабе. Вместе с тем, потребуется развитие компетенций внутри компании и внедрение MLOps.
На длинном горизонте это решение выглядит оптимальным для QuantumForge с точки зрения стоимости и контроля.
